# ADR-0003「库内 _mcp_* 字段授权模型」专家设计评审报告

- **评审对象**：`docs/adr/0003-permission-fields-model.md`（状态 accepted，2026-10-03）及已落地实现（提交 `018ab50`）
- **评审日期**：2026-10-03
- **评审方法**：三位独立专家并行分域评审（字段体系与权限模型 / 安全护栏可绕过性 / 交互合理性），组织方对全部高严重度结论逐行独立复核；全程只读，未改动任何代码
- **评审基线**：以下已拍板决策不作重开（Q1 token 并集、Q2 自动创建默认条目、Q4 旧条目直删不回退、六项 default 字段、删除=回收站取代审批弹窗）

---

## 一、总体结论

**可行，但需修改后进入 P8/发布。** 核心判定链（条目显式字段 → 首个配置条目 default → 硬编码三级）、reserved_field 拒绝 `_mcp_` 前缀写入、读出口掩码、token 恒定时间比较与回环绑定四道主闸门均成立，探针 196/196 覆盖路径无越权读密/提权路径；**无阻断级问题**。但存在 **6 项高严重度**问题（其中 2 项为可利用的越权缺口：`restore_backup` 路径遍历、`restore_backup` 逐条目写拒绝旁路）、10 项中、7 项低，以及 2 处"文档契约与实现不符"（`_mcp_server=0` 停监听被忽略、无鉴权态不可达），需修补后再行发布。

---

## 二、问题清单（按严重度排序）

### 高严重度

**H1. `restore_backup` backupId 直接路径拼接，客户端可控 → 路径遍历 + 内容回显 + 定向篡改**
- **问题**：`RestoreBackup` 用 `Path.Combine(BackupsDir, backupId + ".json")`，`backupId` 直接来自客户端参数，无任何白名单/净化。
- **影响**：已鉴权客户端传入 `../../…` 可读取本机任意可读 `.json`；dry_run 模式会把该文件 `entries[].uuid/title/custom_fields` 值填入 changes 响应回显（变相文件读取出口）；执行态还会把伪造备份中的非保护字段写回 UUID 匹配的活条目。
- **建议**：backupId 白名单正则（仅 `^\d{14}_[a-z_]+_[0-9a-f]{8}$` 之类），拒绝含 `..`/路径分隔符的值；或仅从 BackupsDir 列目录精确匹配。
- **证据**：`src/KeePassMCP/Core/WriteHandlers.cs:409`（`Path.Combine`）、`:413`（直接 ReadAllText）、`:417-496`（dry_run 回显）、`:498-499`（Set 回写）。已复核。

**H2. `restore_backup` 恢复循环无逐条目 Write 判定，绕过显式 `_mcp_write=0`**
- **问题**：恢复前仅做一次全局 `RequirePermission(db, null, Write)`，随后对备份内每个条目统一 `Strings.Set(...)`，循环内不再调用 `ResolvePermission(该条目, Write)`。
- **影响**：默认配置（`_mcp_write_default=1`）下，被显式锁定（`_mcp_write=0`）的条目其 Title/UserName/URL/Notes/非保护 custom 字段可被批量回写篡改，逐条目写拒绝在批量恢复面上失效。保护字段被 skipNames 跳过，故无明文外泄、无提权。
- **建议**：恢复循环内对每个待恢复条目补 `ResolvePermission(entry, Write)` 闸门（保留全局闸门）；无权限条目标记 `restore_skip`。
- **证据**：`src/KeePassMCP/Core/WriteHandlers.cs:407`（全局闸门）、`:420-482`（循环无 per-entry 判定）、`:498-499`；对照 `UpdateEntryFields` 逐条目闸门 `:84-94`；`LibraryConfig.ResolvePermission:188-205`。已复核。

**H3. `_mcp_server=0` 停监听开关被宿主完全忽略，字段名存实亡**
- **问题**：ADR-0003 字段表承诺 `_mcp_server`="启用监听"开关，但 `McpServerHost.ResolveListeningSpecs`/`Start` 只读 `_mcp_listening`，从未调用 `LibraryConfig.IsServerEnabled`（全 src 仅探针命中）。
- **影响**：用户在 KeePass 界面设 `_mcp_server=0` 以为已关停服务，HttpListener 照常绑定（若此前设过 `0.0.0.0:6789` 则仍在局域网监听），token 仍随 connection.json 分发——安全心理模型完全失效。
- **建议**：`Start/RefreshToken` 遍历配置条目，全部 `_mcp_server` 为假时 Stop 且不启动；探针补 `_mcp_server=0 → listener 不绑定` 断言。
- **证据**：`src/KeePassMCP/MCP/McpServerHost.cs:76-84`、`:124-153`（无 IsServerEnabled 调用）；`LibraryConfig.cs:56-57`（定义存在但零引用）。已复核。

**H4. 回收站中的配置条目仍被收集生效，"删除=停用"的直觉不成立**
- **问题**：`CollectConfigEntries` 对库树无差别递归，未排除 `db.RecycleBinUuid` 指向的组。用户按 KeePass 直觉"删掉 MCPServerConfiguration 条目=停用 MCP"，实际该条目进回收站后仍被收集 → token 继续参与并集鉴权、服务继续监听。
- **影响**：用户误以为已停用/清除鉴权；"删了重配"时新旧 token 并集同时生效，排查困难。
- **建议**：遍历时跳过回收站组（或 ADR 明文规定"停用=设 `_mcp_server=0` 而非删除"）。
- **证据**：`src/KeePassMCP/Core/LibraryConfig.cs:100-107`；对照 ADR-0003 删除=回收站的语义假设。已复核。

**H5. 多配置条目聚合规则不一致：token/监听是并集，default 只取"第一个"且缺字段不回落**
- **问题**：`CollectTokens`/`CollectListeningSpecs` 是跨条目并集，六项 default 却经 `FindFirstConfigEntry`（树遍历第一个）取值；该条目缺字段（dv==null）时直接落硬编码，**不回落次个配置条目**。且"第一个"随条目排序漂移。
- **影响**：用户在第二个配置条目收紧 default 无效（静默忽略）→ 权限模型不可复现，"以为收紧了实则放开"；排序一变生效源就变。
- **建议**：二选一并写入 ADR：(a) default 跨配置条目取"首个非空值"或布尔最严；(b) 明确"default 只认第一个配置条目"并固化首个（固定标题/标记），ConfigForm 标注当前生效源。
- **证据**：`src/KeePassMCP/Core/LibraryConfig.cs:110-114`（all[0]）、`:196-202`（dv==null 不回落）、`:121-152`（token/监听并集不对称）；ADR 表仅写"并集生效"。已复核。

**H6. P7 配置 tab 未实现，六权限/六 default 退化为原生 Advanced 页手敲下划线字段名，无引导、无校验、无反馈**
- **问题**：全 src 无 `PwEntryForm`/`m_tabMain` 注入代码（ConfigForm 仅一行"开发中"hint）；用户授权某条目需手敲 `_mcp_read_protected` 等字段名。字段名拼错（如 `_mcp_red`）`ReadMcpField` 返回 null → 静默落到 default，**用户以为已收紧、实际没生效，KeePass 零提示**；值写 `yes/on` 一律判"关闭"。
- **影响**：非技术用户基本无法正确配置条目级权限；静默失败制造"伪造的安全感"，比没有功能更糟。
- **建议**：(a) 落地 P7 tab（KPEntryTemplates 范式：CheckBox 由插件写正确字段名）；(b) ConfigForm 加"字段体检"：扫描 `_mcp*` 开头不识别字段名并告警；(c) 非法值记审计/提示。
- **证据**：`src/KeePassMCP/UI/ConfigForm.cs:64-66`；`LibraryConfig.cs:84-85`（IsFlagTrue 白名单）、`:191-195`（静默回退）；`docs/HANDOFF.md:406`（P7 待实施）。

### 中严重度

**M1. 配置条目自身可被 move/rename/delete_group 销毁，授权配置完整性可被 API 破坏**
- **问题**：`MoveEntry`/`RenameEntry` 对配置条目同样走 `RequirePermission(entry, Move/Write)`，配置条目无显式字段 → 落到 default（放行）；配合 `create_group`+`move_entry`+`delete_group` 可整体删除 `_mcp_config` 条目。
- **影响**：自定义监听地址/权限基线被静默重置，`EnsureDefaultConfig` 重建全新随机 token（旧 token 失效，自限，无提权，属可用性 DoS）。
- **建议**：move/rename/update 入口对 `IsConfigEntry(entry)` 加硬保护（禁改/禁搬，仅 KeePass UI 可动）。
- **证据**：`src/KeePassMCP/Core/WriteHandlers.cs:56,135`；`LibraryConfig.cs:178-185`（Move/Write 硬编码 true）、`:54`；`:336-340`（DeleteGroup 真删组树）。

**M2. `read_secret` 收集保护字段未排除 `_mcp_` 前缀，护栏①口径分裂**
- **问题**：`ReadSecret` 收集条件为 `key=="Password" || ps.IsProtected`，未叠加 `IsMcpField` 过滤；`MaskedEntrySerializer` 已用 IsMasked 拦截，`read_secret` 走另一套判定未对齐。
- **影响**：窄场景（用户在 KeePass UI 手工给普通条目勾选内存保护的 `_mcp_*` 字段，且已授 `_mcp_read_protected=1`）下该字段明文可被读出；Agent 无法自行创建 `_mcp_` 字段，攻击面窄。
- **建议**：收集与取值统一跳过 `LibraryConfig.IsMcpField(key)`。
- **证据**：`src/KeePassMCP/Core/SecretHandlers.cs:43-49`、`:64-66`；对照 `MaskedEntrySerializer.cs:119`。已复核。

**M3. `get_audit_log` 无任何权限闸门，构成越权元数据读出口与隐信道**
- **问题**：ToolRegistry 直接把 `get_audit_log` 接到 `AuditLog.ReadRecent`，不经过任何 ResolvePermission；审计含 entry_uuid、标题、目标分组、被拒事件。
- **影响**：持有 token 的客户端可枚举全库 uuid 与操作历史；配合 M4 可从"read_secret denied 记录"推断隐身/受限条目存在性，旁路 `_mcp_list=0`。
- **建议**：新增独立权限位（如 `_mcp_audit_default`，默认 0）或从默认工具表移除。
- **证据**：`src/KeePassMCP/MCP/ToolRegistry.cs:271-275`；对照 `SecretHandlers.cs:35-37`。已复核。

**M4. 写/移动/删除类权限拒绝事件一律不落审计，越权尝试无痕**
- **问题**：所有写工具的 `RequirePermission` 拒绝分支在 `RunWrite` 之前 return，而审计只在 apply 成功后落盘；唯 `read_secret` 拒绝被审计。
- **影响**：rename/move/delete 被拒（含 uuid 枚举试探）事后无法溯源。
- **建议**：拒绝分支与 confirm_required 统一补 `denied:"permission_denied"` 审计记录。
- **证据**：`src/KeePassMCP/Core/WriteHandlers.cs:30-37,56-57,85-94,135-136,319-322,370-371,405-408`、`:523-548`。

**M5. 多库场景配置无作用域：任一打开库的 `_mcp_config=1` 条目静默并入 token/监听集**
- **问题**：`FindConfigEntries` 遍历全部打开库，token/监听跨库并集；default 取"第一个"（库打开顺序敏感）；`EnsureDefaultConfig` 落在第一个打开库（可能是共享库）。读路径（整库列表）与写路径（单库）的 default 来源库范围不一致。
- **影响**：配置条目被复制到共享库即成为本机鉴权/监听源；攻击者能在共享库放一条 `_mcp_config=1`（自定 token + `0.0.0.0:8080`）即在用户机器新增放行 token 并扩绑局域网地址。
- **建议**：新增配置作用域字段（见字段增补 §_mcp_scope_self）或 EnsureDefaultConfig 只落当前活动库；default 聚合取最严。
- **证据**：`src/KeePassMCP/Core/LibraryConfig.cs:89-98,110-114,121-152,217`；`McpServerHost.cs:60-61,78`；`WriteHandlers.cs:27-28`（单库）对照 `ToolHandlers.cs:121-122,142-144,181-182`（整库）。

**M6. `backup_database` 无权限闸门；快照不滤隐身条目；备份目录与审计文件 ACL 未收窄**
- **问题**：`BackupDatabase` 无任何 RequirePermission，任何已鉴权客户端可触发整库快照写盘；`BackupStore.CollectEntries` 除配置条目外全收（含 `_mcp_list=0` 隐身条目，其 Title/UserName/URL/Notes 明文落盘）；仅 token 文件与 connection.json 做了 RestrictAcl，`backups\` 与 audit 文件本机可读。
- **影响**：隐身语义在备份介质上被击穿；本机任意进程可读全量明文非保护字段。
- **建议**：快照跳过 List=false 条目；BackupsDir/AuditFile 同样 RestrictAcl；backup 挂默认拒绝权限位。
- **证据**：`src/KeePassMCP/Core/WriteHandlers.cs:384-399`；`BackupStore.cs:78-87`；`AuthToken.cs:44-56`。

**M7. 自动创建的 MCPServerConfiguration 对用户完全静默，入口不可发现**
- **问题**：`EnsureDefaultConfig` 只写 Log 文件，无 UI 通知、无专属图标（P8 待实施）；下次开库根目录突然出现陌生条目，用户不知其来历与作用；只置 `Modified=true` 不强制保存。
- **影响**：可发现性差，用户不知道 MCP 已在跑；误删/误改→客户端 401 或鉴权漂移且无头绪。
- **建议**：创建后弹提示或在 ConfigForm 常驻"已自动创建配置条目，点此定位"；提醒保存；尽早落地 P8 图标/颜色。
- **证据**：`src/KeePassMCP/Core/LibraryConfig.cs:214-245`（仅 Log.Write）、`:236`；`docs/HANDOFF.md:263,407`。

**M8. 端口占用自动 +1 结果不回写库，ConfigForm 也不展示配置条目/token 来源，两个"事实源"脱节**
- **问题**：端口 +1 后实际端口只写 connection.json，库内 `_mcp_listening` 保持原值；ConfigForm 服务状态区只读 connection.json，不列出命中几个配置条目、token 来自哪条、default 由谁决定。
- **影响**：用户照库内字段值配置客户端连不上；多配置并集对用户不可审计，吊销 token 需手敲 `;` 拼接。
- **建议**：+1 时状态区醒目提示实际端口；状态区加"生效配置条目 N 个（标题列表）/token M 个"；tab 提供逐条 token 编辑。
- **证据**：`src/KeePassMCP/MCP/McpServerHost.cs:132-146,563-593`；`src/KeePassMCP/UI/ConfigForm.cs:84-108`。

### 低严重度

**L1. "token 并集为空 → 取消鉴权（仅回环）"契约实际不可达**
- **问题**：`ResolveTokens` 在库内 token 为空时回退 `AuthToken.GetOrCreate()`，`_activeTokens` 永不为空；`VerifyToken` 的 `Count==0→true` 分支是死代码。
- **影响**：方向是失败关闭（比 ADR 更安全），但文档契约不成立；"无鉴权态仅限回环"这条护栏从未被执行验证。
- **建议**：文档改为"空集=回退持久化 token"，或显式实现真无鉴权态并强制回环绑定校验。
- **证据**：`src/KeePassMCP/MCP/McpServerHost.cs:56-73,507-519`；`LibraryConfig.cs:121-135`。已复核。

**L2. 分组树 `entry_count` 未滤隐身/配置条目，存在性可探测**
- **问题**：`BuildGroupTree`/`list_databases` 用 `GetEntriesCount(true)` 全量计数，与 list_entries 返回数之差可推知隐身条目数量。
- **建议**：按 List 权限过滤后计数，或文档明确计数为全量口径。
- **证据**：`src/KeePassMCP/Core/ToolHandlers.cs:266`、`:63-64`。

**L3. 端口重试耗尽后的回退地址拼接 bug**
- **问题**：`$"127.0.0.1:{LibraryConfig.DefaultListening}"`（DefaultListening=`127.0.0.1:6789`）拼出 `127.0.0.1:127.0.0.1:6789` 非法前缀，异常被吞，服务彻底不启动（仅 50 个端口全占时触发）。
- **建议**：回退地址改为实际端口变量或固定 0 由系统分配。
- **证据**：`src/KeePassMCP/MCP/McpServerHost.cs:144`；`LibraryConfig.cs:46`。已复核。

**L4. 写工具不校验 `_mcp_list` 隐身（观察项，非逃逸）**
- **问题**：rename/update/move/add_tag 只判 Write/Move 不判 List——已知 UUID 的隐身条目仍可被改（UUID 128bit 难枚举，实际风险低）；`read_secret` 不要求 `_mcp_read` 只要求 `_mcp_read_protected`（两轴自洽）。
- **建议**：文档明确"`_mcp_list=0` 仅作用于读/枚举，写以 Write/Move 为准"。
- **证据**：`src/KeePassMCP/Core/WriteHandlers.cs:56,84-94,135,351,370`；`SecretHandlers.cs:32-40`。

**L5. 权限字段命名与真实语义错位：`move` 实际含"删除"，`list` 实际是"客户端可见性"**
- **问题**：`_mcp_move` 语义含删除（删除=移回收站）但用户只理解为移动分组；`_mcp_list=0` 是"对 MCP 客户端隐身"易被理解为"KeePass 内隐藏"。`read_protected/write_protected` 复用 KeePass Protect 词汇，正面一致，建议保留。
- **建议**：P7 tab 落地时用中文复选框文案承载真实语义，字段名保持机器协议不变。
- **证据**：`docs/adr/0003-permission-fields-model.md:21-22,28`。

**L6. 普通条目读出口透出 `_mcp_*` 键名（设计如此，仅登记）**
- **问题**：掩码字段键名进入 `protected_field_names` 原样返回（值恒为 `[protected]`），客户端可枚举哪些条目被授过权；无值泄露。
- **建议**：如需收紧，`_mcp_*` 键名用占位符替代；当前可接受。
- **证据**：`src/KeePassMCP/Core/MaskedEntrySerializer.cs:53-60`；探针 `Program.cs:696-699`（显式断言此行为）。

**L7. `_mcp_*` 字段裸露在原生 Advanced 页，误删即静默失权**
- **问题**：除 token 外字段均非保护、默认可见可删；用户在 Advanced 页清理字段时误删 `_mcp_config=1`/`_mcp_read`，插件无提示，条目退出配置集/权限回退。
- **建议**：配合 P7 tab 由插件写入/编辑；FileSaved 钩子检测关键字段消失并提示。
- **证据**：`src/KeePassMCP/Core/LibraryConfig.cs:224-234`；`docs/HANDOFF.md:263`。

## 三、已验证无缺口项（复核确认）

以下护栏经专家逐条验证 + 组织方抽查，确认成立：

1. **reserved_field 双入口拒绝**：create/update 均对 `_mcp_` 前缀（OrdinalIgnoreCase）拒绝，客户端无法注入/改写权限字段（`WriteHandlers.cs:39-47,78,169`；探针 p6 用例全绿）。
2. **配置条目判定基于 `_mcp_config` 字段而非标题**：rename/move 后整条目掩码、备份排除仍生效（`LibraryConfig.cs:53-54`）。
3. **配置条目排除写前快照与整库快照**（`BackupStore.cs:43,84`）。
4. **token 恒定时间 XOR 比较、Host 头白名单防 DNS 重绑定、端口 +1 重试保留回环 host**（`McpServerHost.cs:155-172,310-321,507-519`）。
5. **`_mcp_list=0` 在 list/search/get_entry/read_secret 四处一致过滤**（`ToolHandlers.cs:121,142,181`；`SecretHandlers.cs:23-25`）。
6. **备份中 `_mcp_` 值掩码、restore 经 protected_field_names 白名单跳过 `_mcp_` 字段**（探针 `Program.cs:690,707`；`WriteHandlers.cs:441-445`）——即 restore 不会篡改权限字段。
7. **`IsFlagTrue` 值解析健壮**：仅认 `1`/忽略大小写 `true`，其余一律安全失败→拒绝；空/空白归一为 null→回落下一级（"缺省"与"显式 0"语义正确区分）；大小写与首尾空白已 Trim 兼容。

9. **配置条目读出口/备份保护**：整条目掩码 `["*"]`、`read_secret` token_entry_protected、备份排除配置条目 uuid，探针断言齐备。
10. **删除=回收站且客户端无永久删除工具**（但回收站条目仍生效，见 H4）。

## 四、字段表增补建议

**新增字段（2 位专家共同主张，建议采纳）：**

| 字段 | 默认值 | 语义 | 理由 |
|---|---|---|---|
| `_mcp_scope_self` | `0` | `1` = 该配置条目仅对所属库生效，token/listening/default 不并入全局集 | 封堵多库场景共享库配置条目静默并入（M5） |
| `_mcp_audit_default` | `0` | `1` 才允许客户端读 get_audit_log | 给全局审计出口独立权限位（M3） |
| `_mcp_backup_default` | `0` | `1` 才允许触发 backup_database | 给全库快照出口权限位（M6） |

**语义定稿（非新字段，必须落实/写入 ADR）：**
1. `_mcp_server=0` 的停监听语义必须真正生效（H3），否则该字段名存实亡。
2. 多配置条目 default 聚合规则显式定稿：**取"首个非空值"或布尔最严**，并消除排序漂移（H5）；token/监听保持并集。
3. ADR 补一句：`_mcp_server=0` 即停用监听；无配置条目时按 Q2 自动建默认（回环+随机 token）。

**明确不建议新增（字段体系专家论证，理由成立）：**
- **按组/按库配置范围字段（权限粒度角度）**：现有逐条目覆盖（六项 entry 字段优先于 default）已足够精细；组级 default 需改造 PwGroup 承载字段，成本高且与"授权随条目走"决策相悖。此与 `_mcp_scope_self` 不冲突——前者管普通条目权限粒度，后者管配置条目本身的作用域。
- **`_mcp_delete_default`**：删除已并入 Move，六权限足够，新增与"删除=回收站可回滚"决策冗余。
- **显式"关闭自动创建"开关**：`EnsureDefaultConfig` 仅在库内零配置条目时触发，`_mcp_server=0` 已等价于总开关，新增反而增加"状态藏哪"的歧义。
